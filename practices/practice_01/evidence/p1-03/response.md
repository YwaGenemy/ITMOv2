# Проектный черновик: Учебный AI-помощник Code Review

## Проблема и пользователь
**Проблема:** Студенты не умеют формулировать точные промпты для LLM-ревьюера и не проверяют качество ответа по воспроизводимым критериям. Существующие подходы дают размытые советы без привязки к строкам diff и правилам репозитория.

**Пользователь:** Студент ИТМО, выполняющий практикумум по AI-assisted code review. Работает с фиксированным `TRAINING_PR.diff` в своём форке, использует OpenCode в режиме анализа. Цель — научиться собирать Context Pack и оценивать ответы LLM по четким признакам.

---

## 3 измеримых метрики (baseline неизвестен, цели — гипотезы)

| Метрика | Гипотеза цели | Комментарий |
|---------|---------------|-------------|
| **Precision@3 risks** — доля рисков с валидной ссылкой на файл:строку и доказательством из diff/правила | ≥ 0.7 | Измеряется на 2-м запуске (с master prompt) по 4 признакам оценки |
| **Recall критических нарушений** — найдено / существующих в diff нарушений SEC-1, API-1, OUT-1 | ≥ 0.8 | Требует эталонного списка нарушений в TRAINING_PR.diff (проектное решение: подготовить заранее) |
| **Format compliance rate** — % запусков, где ответ соответствует OUT-1 (summary, risks[], checks[]) без парсинговых ошибок | ≥ 0.95 | Ошибка формата LLM должна отличаться от timeout и request error (проектное решение) |

## 4 User Stories

1. **Как студент, я хочу отправить только diff и получить базовый ответ LLM, чтобы зафиксировать нулевую точку качества без контекста.**  
   *Критерий приёмки: сохранён запрос, ответ, 3 слабых места, список недостающей информации в prompts.md.*

2. **Как студент, я хочу собрать Context Pack из правил репозитория (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1), применимых к TRAINING_PR.diff, чтобы master prompt содержал только релевантные факты.**  
   *Критерий приёмки: в Context Pack нет правил про snake_case и i18n; каждый пункт трактуется на конкретный файл/строку diff.*

3. **Как студент, я хочу запустить master prompt с тем же diff и сравнить ответы по 4 признакам (ссылка на файл:строка, подтверждение diff/правилом, границы помощника, воспроизводимая проверка), чтобы увидеть прирост качества.**  
   *Критерий приёмки: таблица сравнения в prompts.md с вердиктом по каждому признаку.*

4. **Как преподаватель, я хочу видеть в логах только request_id, длительность и статус (OBS-1), чтобы содержимое diff и ответов модели не утекало.**  
   *Критерий приёмки: проверка логов после обоих запусков.*

## Границы ответственности API / Service / LLM

| Слой | Отвечает за | Не отвечает за |
|------|-------------|----------------|
| **API (HTTP вход)** | Валидация размера diff (API-1: >20k → 413); санитизация секретов перед проксированием (SEC-1); возврат структурированных ошибок: `request_error` (400), `timeout` (504), `llm_format_error` (502) | Содержимое проверок, логика промптов, вызов LLM |
| **Service (оркестратор)** | Сборка master prompt из шаблона + Context Pack + diff; управление таймаутом REL-1 (10с); нормализация ответа под OUT-1; логирование OBS-1 | Генерация текста рисков, решение о merge/approve |
| **LLM (внешний)** | Только генерация текста по переданному промпту | Доступ к коду, выполнение проверок, знание правил репозитория |

*Проектное решение: три типа ошибок различаются по HTTP коду и полю `error_type` в теле ответа.*

## Порядок проверок (последовательность в Service)

1. **Валидация входа** — размер diff ≤ 20k символов (API-1) → иначе 413.
2. **Санитизация** — удаление токенов/ключей из diff (SEC-1) перед передаче LLM.
3. **Сборка промпта** — мастер-промпт = шаблон (8 вопросов) + Context Pack (только применимые правила) + чистый diff.
4. **Вызов LLM с таймаутом 10с** (REL-1) → при превышении: возврат контролируемого ответа с `error_type=timeout`.
5. **Парсинг и валидация схемы OUT-1** — обязательные поля `summary`, `risks[]` (≤3, каждый с `file,line,evidence,risk`), `checks[]` → при несоответствии: `error_type=llm_format_error`.
6. **Фильтр QA-1** — отбрасывание рисков без подтверждения строкой diff или правилом репозитория.
7. **Логирование OBS-1** — только `request_id`, `duration_ms`, `status` (success/request_error/timeout/llm_format_error).
8. **Возврат клиенту** — JSON по OUT-1 или структурированная ошибка.

## 8 тестовых сценариев

| ID | Сценарий | Вход | Ожидаемый результат | Тип ошибки |
|----|----------|------|---------------------|------------|
| T1 | Нормальный diff ≤20k, валидный ответ LLM | TRAINING_PR.diff + master prompt | 200, OUT-1 схема, risks ≤3, каждый с file:line:evidence | — |
| T2 | Diff >20k символов | Сгенерированный diff 25k | 413, `error_type=request_error` | request_error |
| T3 | Diff содержит токен `ghp_xxx` | diff с вставленным секретом | В промпте LLM токен заменён на `[REDACTED]` (проверка по логам промпта) | — |
| T4 | LLM не отвечает 10с | Мок LLM с задержкой 15с | 504, `error_type=timeout`, ответ содержит summary="timeout" | timeout |
| T5 | LLM вернул невалидный JSON | Мок LLM: текст без JSON | 502, `error_type=llm_format_error` | llm_format_error |
| T6 | LLM вернул 4 риска | Мок LLM: risks.length=4 | В ответе клиенту risks.length=3 (обрезка/отбраковка) | — |
| T7 | Риск без доказательства в diff | Мок LLM: risk с несуществующим file:line | Риск отфильтрован QA-1, не попадает в ответ | — |
| T8 | Логи не содержат diff/ответ | Любой успешный запуск | В логе только request_id, duration_ms, status=success | — |

*Гипотеза: сценарии T2–T5 покрывают все различимые классы ошибок; T6–T7 проверяют границы OUT-1 и QA-1.*

## CASE — требования (из источника, без изменений)

- SEC-1: санитизация секретов перед внешним LLM
- API-1: diff >20k → HTTP 413
- REL-1: timeout 10с → контролируемый ответ
- OUT-1: схема `summary`, `risks[]` (≤3, file/line/evidence/risk), `checks[]`
- SCOPE-1: только советы, нет approve/merge/code changes
- QA-1: риск только с подтверждением строкой diff или правилом
- OBS-1: логи только request_id, duration, status

*Правила про snake_case и i18n — явно исключены из Context Pack (источник).*

---

## Проектные решения и гипотезы (маркировка)

1. **Проектное решение:** Три класса ошибок (`request_error`, `timeout`, `llm_format_error`) с разными HTTP кодами и полем `error_type`.
2. **Проектное решение:** Эталонный список нарушений в TRAINING_PR.diff готовится заранее для измерения Recall.
3. **Гипотеза:** Precision@3 ≥ 0.7 достижима на 2-м запуске при соблюдении.master prompt структуры.
4. **Гипотеза:** Format compliance ≥ 0.95 при валидации OUT-1 на стороне Service.
5. **Проектное решение:** Студент не меняет master prompt устно во 2-м запуске — только приложенный файл и сохранённый промпт.
6. **Гипотеза:** 8 тестовых сценариев достаточно для верификации границ API/Service/LLM без работающего бэкенда.
