## P1-02

Сохранённый ответ:

```prompt
Описание изменений:
- Добавлен метод review() в ReviewService, который принимает diff и возвращает комментарий от LLM
- Добавлен эндпоинт POST /api/reviews в api.py, который принимает JSON с полем diff и вызывает сервис
Подтвержденные риски:
1. Отсутствие валидации входных данных (app/api.py:36-37) — прямое обращение payload["diff"] вызовет KeyError, если поле отсутствует. Нет Pydantic-модели для валидации схемы запроса.
2. Отсутствие обработки ошибок LLM (app/review_service.py:21-22) — исключения от llm.generate() пробросятся наружу как 500 без логирования или понятного ответа клиенту.
3. Инъекция в промпт (app/review_service.py:20) — пользовательский diff напрямую подставляется в f-string без санитизации/экранирования. Злоумышленник может манипулировать инструкциями к LLM через специально сформированный diff.
Конкретные проверки:
1. Добавить Pydantic-модель ReviewRequest(diff: str) и использовать её в эндпоинте
2. Обернуть вызов llm.generate() в try/except, возвращать структурированную ошибку (например, {"error": "llm_failed"})
3. Экранировать/лимитировать diff перед вставкой в промпт (обрезать длину, экранировать спецсимволы, или использовать шаблонизатор с автоэкранированием)
```

## Master Prompt v2 - доработка после P1-02

Контракт ниже подготовлен для повторного использования. Он не был частью сохранённого запуска P1-02; результат P1-02 не приписывается этому тексту.

### 1. Цель и роль

- Цель: найти проверяемые проблемы в одном учебном diff.
- Роль AI: помощник ревьюера; окончательное решение принимает человек.

### 2. Входы и источники

- Обязательный вход: приложенный TRAINING_PR.diff.
- Разрешённые источники: только diff и этот текст запроса.
- Context Pack: SEC-1 - удалить токены, пароли и приватные ключи до внешнего LLM; API-1 - более 20 000 символов дают HTTP 413; REL-1 - timeout 10 секунд и контролируемая ошибка; OUT-1 - summary, risks, checks, максимум три риска с file, line, evidence, risk; SCOPE-1 - только советы; QA-1 - каждый риск обоснован diff или правилом; OBS-1 - в логах только request_id, длительность, статус, без diff и ответа модели.

### 3. Задача и артефакты

- Что сделать: сопоставить изменения с правилами, выбрать до трёх наиболее важных доказанных рисков.
- Что вернуть: описание изменения, риски и проверки, без изменения кода.

### 4. Формат результата

- Структура ответа: summary (строка), risks (массив file, line, evidence, risk), checks (массив конкретных проверок с входом и ожидаемым результатом).
- Ограничение: максимум три риска; line - строка новой версии файла, не строка файла patch. Если номер нельзя достоверно определить, объясни ограничение вне списка рисков.

### 5. Полномочия и запреты

- Разрешено: анализировать приложенный текст и явно отмечать неизвестное.
- Запрещено: web, shell, чтение других файлов, правки, действия в GitHub и выдуманные результаты тестов.

### 6. Рабочий процесс и остановка

- Шаги: описать изменение → сверить правила → проверить основания замечаний → предложить проверки.
- Остановка: вернуть результат после проверки каждого замечания. Если нужен отсутствующий адаптер или middleware, сообщить, какой вывод без него не подтверждается; не искать его самостоятельно.

### 7. Проверки и evidence

- Проверка: каждый риск сопровождается фрагментом diff или конкретным правилом. Отсутствие компонента в diff не доказывает его отсутствия в проекте.
- Хорошо: «diff передаётся в LLM без очистки в показанном методе; SEC-1; тест с синтетическим токеном и fake LLM». Плохо: «в проекте точно нет авторизации».
- Evidence: сохранить ответ, модель и список предлагаемых тестов; тесты не считать запущенными.

### 8. Definition of Done

- Задача закончена, когда все риски имеют доказательства, неизвестное обозначено и для каждого риска есть воспроизводимая проверка.

## Сравнение двух запусков

| Проверка | Zero-shot | С master prompt | Вывод команды |
|---|---|---|---|
| Есть ссылка на файл или строку | Нет точных ссылок | Указаны файлы, но номера относятся к строкам TRAINING_PR.diff, а не к названным Python-файлам | Привязка появилась, нумерация требует исправления |
| Вывод подтверждён diff или правилом | KeyError обоснован; авторизация и инициализация зависимости не доказаны | KeyError обоснован; глобальная обработка ошибок и логирование неизвестны. SEC-1, API-1 и OUT-1 не разобраны | Контекст правил использован недостаточно |
| Соблюдены границы AI | В ответе только замечания | В ответе только замечания и рекомендации | По тексту нельзя подтвердить отсутствие вызовов инструментов |
| Есть воспроизводимая проверка | Нет | Вместо проверок предложены изменения кода | Нужны вход и ожидаемый результат, например JSON без diff и контролируемый отказ |

Дополнительная оценка P1-02: автоэкранирование не гарантирует защиту от инструкций внутри diff. Обрезание diff противоречит API-1: для длины свыше 20 000 символов требуется HTTP 413. Отсутствие локального try/except видно, но без кода адаптера и глобальных обработчиков нельзя утверждать, что клиент обязательно получит неконтролируемый 500 и что логирования нет.

## Оценка P1-01 и недостающий контекст

Три слабых места: отсутствие авторизации и ошибка инициализации не доказаны; перенос `...` не меняет поведение; нет координат и воспроизводимых проверок. Модели не были переданы правила CASE, реализация адаптера LLM, middleware и контракт ошибок.

Для первого запуска предлагался запрос «Ниже diff учебного PR. Посмотри PR и найди проблемы.». Точный ввод и логи действий не сохранены. Для P1-02 модель отдельно не зафиксирована.
