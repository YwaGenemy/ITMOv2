# Общий контракт команд 1 (UI) и 2 (логика/API)

**Дата согласования**: 2026-10-27. **Статус**: решения человека D1–D6 приняты; A-01–A-05 закрыты.

Базовый источник требований — [docs/requirements.md](../docs/requirements.md). Этот документ фиксирует интеграционные решения человека для [UI](001-reviewer-web-ui/spec.md) и [API](002-review-api-deadline/spec.md), не изменяя базовые требования. Проверка схемы результата модели на сервере (US-1) остаётся вне этих фич.

## Страница и запрос

- `GET /` обслуживает тот же сервер `app/server.py`, выдавая HTML из `app/static/index.html`. Маршрут и выдача файла — команда 2; содержимое HTML, CSS и клиентский сценарий без фреймворков — команда 1.
- UI обращается к относительному адресу `POST /api/reviews` на том же сервере. Заголовок запроса: `Content-Type: application/json`.
- Тело — JSON-объект с полем `diff`:

```json
{"diff":"diff --git a/example.txt b/example.txt\n..."}
```

- UI локально отклоняет пустое и полностью пробельное поле. Непустой ввод отправляет целиком, без trim, нормализации и обрезания; длину не проверяет.
- Сервер принимает непустую строку длиной не более 20 000 Unicode code points после JSON-декодирования. Ровно 20 000 допустимы. Полностью пробельная строка для API непустая; синтаксис unified diff API не проверяет.
- Неверный JSON, не объект, отсутствие `diff`, нестроковый `diff` или `diff: ""` → 422; превышение длины → 413. В обоих случаях LLM не вызывается, ввод не обрезается.
- `request_id` и `deadline_s` клиент не задаёт. Для допустимого ввода сервер вызывает LLM один раз, без повторов, с лимитом ожидания 10 секунд в HTTP-интеграции. Публичная функция `handle_review(body: bytes, llm, *, deadline_s=10.0)` допускает положительное серверное переопределение лимита для других вызовов и приёмки.

## Ответы и проверка в UI

Ответы API — JSON. Успех — HTTP 200:

```json
{
  "summary": "Изменение проверено",
  "risks": [
    {"file": "example.txt", "line": 1, "evidence": "изменённая строка", "risk": "описание риска"}
  ],
  "checks": ["Проверить граничный случай"],
  "request_id": "f7a5cd9283104ef6a72560aa8cc44701"
}
```

Для отображения успеха UI проверяет обязательные поля:

| Поле | Требование |
| --- | --- |
| `summary` | Строка |
| `risks` | Массив из 0–3 объектов риска |
| `risks[].file`, `evidence`, `risk` | Строки |
| `risks[].line` | Целое число ≥ 1 |
| `checks` | Массив строк; пустой массив допустим |
| `request_id` | Строка; сервис генерирует uuid4 hex (32 шестнадцатеричных символа без дефисов) |

Отсутствие обязательного поля, неверный тип, неверный номер строки или более трёх рисков в JSON-ответе 200 → «Некорректный ответ сервиса». UI не обрезает массивы и не показывает частичный результат. Пустой массив `risks` → успешное состояние «Риски не найдены»; пустой `checks` → «Список проверок пуст». Порядок всех элементов сохраняется, содержимое отображается как текст.

Это проверка данных для отображения в UI, а не серверная гарантия схемы результата модели. Сервер пока не проверяет эту схему, не ограничивает число рисков и не вводит `invalid_llm_output`: это US-1 вне фичи. Своевременный успешный вызов LLM сохраняет ответ 200 существующего API.

Общая форма ошибки API:

```json
{"error":{"code":"llm_timeout"},"request_id":"f7a5cd9283104ef6a72560aa8cc44701"}
```

Сервер генерирует `request_id` для любого исхода, включая неверный JSON. В ошибке `error` содержит только `code`, рядом расположен `request_id`; поля `message`, результат ревью, текст/тип исключения и traceback не возвращаются.

## Ошибки и точные тексты UI

Специальный текст API-ошибки выбирается только по совпавшей паре HTTP-статуса и `error.code`. Неизвестный или отсутствующий код, несовпадение пары, иной статус и не-JSON ответ (включая HTTP 200) дают общую ошибку. Текст сервера и сырой ответ не выводятся.

| Источник / HTTP | Код / условие | Текст UI |
| --- | --- | --- |
| Локальная проверка | Поле пустое или полностью пробельное; запрос не отправляется | Вставьте diff для проверки |
| 422 | `invalid_request` | Не удалось проверить diff. Проверьте введённые изменения и повторите попытку |
| 413 | `diff_too_large` | Diff слишком большой. Максимум — 20 000 символов. Уменьшите diff и повторите попытку |
| 504 | `llm_timeout` | Проверка заняла слишком много времени. Повторите попытку |
| 502 | `llm_failed` | Не удалось выполнить проверку. Повторите попытку позже |
| 200, JSON | Не соответствует схеме успеха выше, в том числе более трёх рисков | Некорректный ответ сервиса |
| Локальный тайм-аут UI | Ответ не получен и не обработан за 15 секунд с начала запроса | Сервис не ответил вовремя |
| Любой другой случай | Другой статус/код, неверная структура ошибки, не JSON, ошибка сети/соединения | Сервис недоступен |

В **любой** ошибке UI дополнительно показывает `request_id`, если он доступен в разобранном ответе, включая некорректный ответ 200 и неизвестный статус/код. Идентификатор отображается как текст с подписью `request_id`, без сырого ответа. Если ответа или идентификатора нет, UI его не выдумывает; это не мешает показать причину ошибки.

## Сроки и состояния страницы

Серверные 10 секунд ограничивают ожидание LLM, а не разбор JSON и доставку ответа. Клиентские 15 секунд ограничивают всё ожидание запроса, включая получение и обработку ответа. При истечении клиентского срока UI завершает загрузку с локальной ошибкой и прекращает ожидание; поздний ответ не меняет состояние и не заменяет результат более новой попытки. Автоматических повторов нет.

| Состояние | Представление | Переходы |
| --- | --- | --- |
| Пусто / ввод | «Ревью изменений», поле «Diff», подсказка «Вставьте diff одного PR», кнопка «Проверить»; при первом открытии результата и ошибки нет | Пустая отправка → ошибка ввода и фокус в поле; непустая → загрузка |
| Загрузка | Ввод сохранён; поле и кнопка заблокированы; кнопка «Проверяем…», статус «Проверяем изменения…»; прежний результат и ошибка скрыты | Валидный 200 → успех с рисками или без; любая ошибка или истечение 15 секунд → ошибка; повторная отправка невозможна |
| Успех | «Сводка», «Риски» с 1–3 полными рисками, «Проверки»; поле и кнопка доступны | Редактирование → ввод без старого результата; отправка → загрузка |
| Успех без рисков | То же, но «Риски не найдены» | Как при успехе |
| Ошибка | Точный текст из таблицы и `request_id`, если доступен; исходный ввод сохранён; поле и кнопка доступны; результата нет | Исправление ввода, ручная повторная отправка → загрузка с очисткой прежней ошибки |

Все завершения запроса разблокируют форму. Ошибка остаётся видна до следующей отправки; прежний результат скрывается также при редактировании diff. После перезагрузки — начальное пустое состояние. Состояния доступны с клавиатуры и сообщаются средствами чтения экрана; diff, evidence и остальные данные не исполняются как HTML.

## Ответственность команд

| Область | Ответственный |
| --- | --- |
| `app/static/index.html`: содержимое, стили, клиентские вызовы, проверка ответа для отображения, 15 секунд, состояния, тексты и показ `request_id` | Команда 1 (UI) |
| `app/server.py`: `GET /`, выдача файла, `POST /api/reviews`, передача статуса и JSON результата логики | Команда 2 (логика/API) |
| Валидация ввода и длины, один вызов LLM, 10 секунд ожидания, ошибки API, генерация `request_id`, логи только `request_id`, `duration_ms`, `status` | Команда 2 (логика/API) |
| Согласованность спецификаций и приёмка интеграции по этому контракту | Обе команды |

## Принятые решения человека

- **D1**: `GET /` отдаёт `app/server.py` из `app/static/index.html`; маршрут — команда 2, содержимое — команда 1.
- **D2**: `POST /api/reviews`, `Content-Type: application/json`, тело `{"diff":"..."}`; UI длину не проверяет и не обрезает, решение принимает сервер.
- **D3**: Успех 200 по контракту. Серверная проверка схемы модели — US-1 вне фичи; более трёх рисков или неверные типы → «Некорректный ответ сервиса» в UI, без обрезания.
- **D4**: Ошибки 422 `invalid_request`, 413 `diff_too_large`, 504 `llm_timeout`, 502 `llm_failed`; прочие статусы/коды и не JSON → «Сервис недоступен». Точные русские тексты закреплены таблицей выше.
- **D5**: UI ждёт не более 15 секунд, сервер — 10 секунд вызова LLM; истечение срока UI → «Сервис не ответил вовремя».
- **D6**: В любой ошибке UI показывает `request_id`, если он есть в ответе.
