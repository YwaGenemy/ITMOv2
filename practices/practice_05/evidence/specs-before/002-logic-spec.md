# Feature Specification: Ограниченное ожидание LLM в API ревью

**Feature Branch**: не назначена; идентификатор фичи — `002-review-api-deadline`

**Created**: 2026-10-27

**Status**: Draft

**Input**: Команда 2, только логика и API. Фича B (US-4): обработка `POST /api/reviews`, ограничение вызова LLM через `deadline_s`, ошибки `504 llm_timeout` и `502 llm_failed` без текста исключения, сохранение валидации фичи A. Описать данные, алгоритм, правила и клиентский контракт. Только спецификация.

**Источник требований**: [docs/requirements.md](../../docs/requirements.md), разделы «Контракт API», «Фича A», «Фича B», «Наблюдаемость». Спецификация конкретизирует их для команды 2, не меняя контракт.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Получить определённый результат при зависании зависимости (Priority: P1)

Как потребитель сервиса ревью, я хочу получить понятный результат по окончании разрешённого ожидания, чтобы запрос не оставался незавершённым из-за LLM.

**Why this priority**: Это основное поведение US-4: доступность ответа клиенту не должна зависеть от завершения медленной зависимости.

**Independent Test**: Отправить корректный запрос при контролируемой задержке зависимости, превышающей установленный лимит; проверить результат и момент возврата независимо от остальных сценариев.

**Acceptance Scenarios**:

1. **Given** корректный запрос и LLM, не завершившая вызов за `deadline_s`, **When** лимит истекает, **Then** возвращаются HTTP 504, `error.code = "llm_timeout"` и `request_id`, без ожидания завершения LLM.
2. **Given** тот же медленный вызов, **When** клиент уже получил 504, **Then** поздний результат или позднее исключение не меняет ответ и не запускает повторный вызов.
3. **Given** корректный запрос и корректный результат LLM до истечения лимита, **When** обработка завершается, **Then** возвращается HTTP 200 с полями `summary`, `risks`, `checks`, `request_id`; LLM вызывается один раз.
4. **Given** лимит явно не переопределён сервисом, **When** начинается вызов LLM, **Then** применяется лимит 10 секунд; при другом положительном `deadline_s` применяется переданное значение.

---

### User Story 2 - Получить безопасную ошибку зависимости (Priority: P1)

Как потребитель сервиса ревью, я хочу отличать сбой зависимости от истечения времени, не получая внутренние сведения из исключения.

**Why this priority**: Код результата должен быть предсказуемым, а внутренние сообщения адаптера не должны раскрываться клиенту.

**Independent Test**: Для корректного запроса задать исключение адаптера с узнаваемым контрольным текстом и проверить весь возвращаемый ответ.

**Acceptance Scenarios**:

1. **Given** адаптер бросает исключение до истечения лимита, **When** сервис получает исключение, **Then** возвращаются HTTP 502, `error.code = "llm_failed"` и `request_id`; повторов нет.
2. **Given** исключение содержит внутренний контрольный текст, **When** формируется ответ, **Then** в нём отсутствуют текст исключения, его тип, traceback и дополнительные поля с диагностикой.
3. **Given** ошибка зависимости, **When** фиксируется результат обработки, **Then** запись лога содержит только `request_id`, `duration_ms`, `status`.

---

### User Story 3 - Сохранить предсказуемую проверку входа (Priority: P1)

Как потребитель сервиса ревью, я хочу получать прежние ошибки для некорректного или слишком большого запроса, чтобы добавление обработки сбоев не нарушало интеграцию.

**Why this priority**: Сохранение всех сценариев фичи A — обязательное условие US-4.

**Independent Test**: Передать набор неверных тел и граничных размеров; проверить статусы, коды, идентификаторы и количество обращений к зависимости.

**Acceptance Scenarios**:

1. **Given** тело не является JSON, **When** оно передано сервису, **Then** возвращается 422 `invalid_request`, LLM не вызывается.
2. **Given** JSON не является объектом, либо `diff` отсутствует, не является строкой или равен пустой строке, **When** запрос проверяется, **Then** возвращается 422 `invalid_request`, LLM не вызывается.
3. **Given** строка `diff` длиной 20 001 Unicode code points, **When** запрос проверяется, **Then** возвращается 413 `diff_too_large`, LLM не вызывается, вход не обрезается.
4. **Given** непустая строка `diff` длиной ровно 20 000 Unicode code points и успешная LLM, **When** запрос обработан, **Then** возвращается 200, а LLM получает исходную строку целиком ровно один раз.
5. **Given** любой из указанных отказов валидации и адаптер, который при вызове завис бы или бросил исключение, **When** запрос обработан, **Then** сохраняется ошибка валидации, адаптер не вызывается.

### Edge Cases

- Пустое тело, JSON `null`, массив, строка, число, булево значение, объект без `diff`, `diff: null`, числовой `diff` и `diff: ""` дают 422.
- Длина считается после JSON-декодирования в Unicode code points, а не в байтах, символах JSON-экранирования или единицах UTF-16. Многобайтовые и экранированные символы входят в граничные проверки 20 000/20 001.
- Строка из пробелов непустая: контракт не требует обрезки пробелов или проверки синтаксиса unified diff.
- При отказе проверки типа `diff` подсчёт длины не выполняется: это 422, а не 413.
- Если к окончанию лимита вызов не завершён, итог — 504; последующее исключение не превращает его в 502.
- Сбой и медленный ответ при корректном вводе не запускают повторов. Валидация всегда предшествует обращению к LLM.
- Любой исход, включая ошибку чтения JSON, содержит сгенерированный сервисом `request_id`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Сервис MUST принимать `POST /api/reviews` с JSON-объектом, содержащим строку `diff`; условия допустимости определены FR-002 и FR-003.
- **FR-002**: Сервис MUST возвращать 422 `invalid_request` для всех случаев неверного ввода из фичи A: не JSON, не объект, отсутствие `diff`, нестроковый или пустой `diff`.
- **FR-003**: Сервис MUST отклонять строку длиннее 20 000 Unicode code points после JSON-декодирования с 413 `diff_too_large`; ровно 20 000 допускаются. Строка MUST NOT обрезаться или нормализоваться перед передачей LLM.
- **FR-004**: При любом отказе валидации сервис MUST выполнять ноль вызовов LLM; при прошедшем валидацию запросе — один вызов без повторов при любом исходе.
- **FR-005**: Ожидание вызова LLM MUST ограничиваться `deadline_s`, по умолчанию 10 секунд. Лимит относится к вызову зависимости, а не к разбору входного JSON или сетевой доставке ответа.
- **FR-006**: По истечении лимита при незавершённом вызове сервис MUST возвращать 504 `llm_timeout`, не ожидая завершения LLM. Поздний исход MUST NOT менять уже выбранный ответ.
- **FR-007**: Исключение адаптера, полученное до истечения лимита, MUST приводить к 502 `llm_failed`; ответ MUST NOT содержать текст, тип исключения, traceback или дополнительные диагностические сведения.
- **FR-008**: Успешный вызов до истечения лимита MUST сохранять ответ 200 существующего контракта: `summary`, `risks`, `checks`, `request_id`.
- **FR-009**: Каждый ответ MUST содержать `request_id`, сгенерированный сервисом в формате uuid4 hex: 32 шестнадцатеричных символа без дефисов. Все ошибки MUST иметь единую форму из раздела «API-контракт для клиентов».
- **FR-010**: Публичная точка входа логики MUST сохраняться: `handle_review(body: bytes, llm, *, deadline_s=10.0)` возвращает `(status: int, payload: dict)`. HTTP-слой MUST передавать этот статус и JSON-представление payload клиенту без переопределения результата.
- **FR-011**: Логи обработки MUST содержать только `request_id`, `duration_ms`, `status`. Diff, результат LLM и сведения об исключениях MUST NOT логироваться. Идентификатор и статус MUST совпадать с ответом; длительность относится к обработке до возврата ответа, включая случай 504.

### Key Entities *(include if feature involves data)*

- **Запрос ревью**: исходное тело запроса и полученная после JSON-декодирования строка `diff`; длина определяет допуск к вызову зависимости.
- **Параметры ожидания**: `deadline_s`, серверный лимит вызова в секундах; не поле запроса клиента.
- **Результат ревью**: `summary` — строка; `risks` — массив рисков; `checks` — массив строк; `request_id` — идентификатор обработки.
- **Риск**: `file` — строка, `line` — целое число не меньше 1, `evidence` — строка, `risk` — строка.
- **Ошибка обработки**: объект `error` с единственным полем `code` и соседний `request_id`; код определяет причину отказа.
- **Запись наблюдаемости**: идентификатор обработки, её длительность в миллисекундах и итоговый HTTP-статус.

### API-контракт для клиентов

**Операция**: `POST /api/reviews`. Формат тела запроса и ответа — JSON; клиент передаёт `Content-Type: application/json`.

Запрос:

```json
{"diff":"diff --git a/example.txt b/example.txt\n..."}
```

Обязательное поле `diff` — непустая строка длиной не более 20 000 Unicode code points после декодирования. `deadline_s` задаёт сервис, клиент не управляет им через тело запроса. Клиенту не требуется передавать `request_id`.

Успех HTTP 200:

```json
{
  "summary": "Изменение проверено",
  "risks": [
    {"file": "example.txt", "line": 1, "evidence": "изменённая строка", "risk": "описание риска"}
  ],
  "checks": ["Проверить граничный случай"],
  "request_id": "f7a5cd9283104ef6a72560aa8cc44701"
}
```

Общая форма ошибки:

```json
{"error":{"code":"llm_timeout"},"request_id":"f7a5cd9283104ef6a72560aa8cc44701"}
```

| HTTP | `error.code` | Условие |
| --- | --- | --- |
| 422 | `invalid_request` | Некорректный JSON или нарушение структуры/типа/непустоты `diff` |
| 413 | `diff_too_large` | Строка `diff` длиннее 20 000 Unicode code points |
| 504 | `llm_timeout` | Вызов LLM не завершён к окончанию `deadline_s` |
| 502 | `llm_failed` | До окончания лимита получено исключение адаптера |

Клиент различает результаты по HTTP-статусу и `error.code`, а `request_id` использует для ссылки на конкретную обработку. Ошибки не содержат поля `message` или полей успешного результата. Повторные попытки на стороне сервиса отсутствуют; политика повторной отправки клиентом этим контрактом не задаётся.

### Алгоритм обработки и приоритет правил

1. Назначить обработке серверный `request_id` и начать измерение её длительности.
2. Разобрать тело как JSON, проверить объект, наличие поля `diff`, его строковый тип и непустоту. При нарушении завершить обработку ответом 422.
3. Посчитать Unicode code points декодированного `diff`. При превышении 20 000 завершить обработку ответом 413; исходную строку не изменять.
4. Для допустимого ввода однократно обратиться к LLM, ограничив ожидание этого вызова значением `deadline_s`.
5. Если до истечения лимита получен успешный результат, вернуть 200 по существующему контракту. Если получено исключение адаптера, вернуть 502 без внутренних сведений.
6. Если вызов остаётся незавершённым к окончанию лимита, вернуть 504 без ожидания его завершения. Не выполнять повторов и не менять ответ по позднему исходу.
7. Для выбранного исхода вернуть статус и payload с тем же `request_id`, зафиксировав только разрешённые поля наблюдаемости. HTTP-слой транслирует результат клиенту.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В 100% контрольных сценариев медленной зависимости потребитель получает результат «время ожидания истекло» по установленному лимиту, до завершения зависимости. Для воспроизводимой приёмки: лимит 0,1 с, задержка зависимости 1 с, возврат не позднее 0,5 с от начала вызова. Запас 0,4 с — допуск измерения в тестовой среде, а не увеличение рабочего лимита.
- **SC-002**: В 100% сценариев исключения до окончания лимита потребитель получает результат «сбой зависимости»; контрольный внутренний текст отсутствует во всём ответе, что позволяет безопасно передавать его для диагностики.
- **SC-003**: Все сценарии фичи A и обе границы 20 000/20 001 проходят приёмку без изменения исходного текста и без обращения к зависимости при отказе.
- **SC-004**: Для каждого допустимого запроса выполняется ровно одна попытка получить ревью; при своевременном успешном результате потребитель получает все четыре поля результата и все обязательные поля каждого риска.
- **SC-005**: Для каждого проверенного исхода потребитель получает идентификатор формата uuid4 hex, совпадающий с идентификатором в записи обработки; записи содержат только три разрешённых поля и не раскрывают содержимое запроса, ревью или исключения.

## Assumptions

- Область фичи — логика обработки и публичный контракт API фичи B с обязательной регрессией фичи A. Проверка схемы результата модели (`invalid_llm_output`, US-1) и очистка секретов (US-2) остаются отдельными историями согласно источнику требований.
- Зависимости спецификации: существующий контракт `docs/requirements.md`, правила `docs/style-guide.md` и принципы `.specify/memory/constitution.md`. Существующий успешный сценарий возвращает корректный результат контракта.
- `deadline_s` — положительный серверный параметр. Некорректная конфигурация лимита, строгий порядок одновременных событий на границе времени и физическая отмена работы адаптера источником требований не определены. Обязательное наблюдаемое поведение — ограниченное ожидание и неизменность уже возвращённого ответа.
- Для воспроизводимой приёмки используются публичная точка входа и `FakeLLM`, без сети и реальных провайдеров; единая команда проверки проекта — `sh scripts/check.sh`. Это ограничения приёмки, а не предписание механизма таймаута.
- Контракт не вводит новых требований к дополнительным полям входного JSON, синтаксису diff или максимальному числу рисков. Пустой считается именно строка нулевой длины.
- Сетевая задержка и доставка ответа клиенту не входят в лимит вызова LLM. Конкретный механизм ограничения ожидания определяется на этапе планирования.
