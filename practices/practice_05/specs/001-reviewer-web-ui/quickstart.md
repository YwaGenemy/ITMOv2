# Проверка веб-страницы ревьюера

Руководство и журнал реализации. Контракты: `specs/contract.md`, `contracts/ui.md`; состояния и типы: `data-model.md`. Фактические результаты приведены в конце документа.

## Подготовка и запуск

Нужны существующее окружение `.venv` с pytest, Python 3.10+ и Node.js с `node:test` (проверено на Node.js 26). Для дополнительной приёмки нужен современный браузер с DevTools. Команды выполнять из корня проекта `practices/practice_05`. Реальная модель и npm-пакеты не нужны.

```sh
sh scripts/check.sh
.venv/bin/python -m app.server 8000 --llm ok
```

Открыть `http://127.0.0.1:8000/`. Сервер использует FakeLLM, обычный ответ — успех без рисков с одной проверкой. Подходящий безопасный ввод: `изменение для проверки` (API не проверяет синтаксис unified diff).

Зафиксировать для каждого нового поведения ожидаемый и фактический результат RED до соответствующего кода, затем повторить тот же сценарий для GREEN. Не заменять исполнение JS поиском строк в HTML. После реализации выполнить `sh scripts/check.sh`; зелёный pytest не заменяет приёмку браузера.

## Реальная локальная интеграция с FakeLLM

1. Начальное состояние: заголовок, метка, подсказка, пустое поле и кнопка; нет результата/ошибки. Вставить ввод и отправить: успех без рисков, сводка и проверки доступны.
2. DevTools → Network: ровно один POST, относительный API того же origin, JSON с исходным diff, Content-Type application/json. Вставка с отступами/переносами сохраняется в декодированном теле.
3. Пустой/пробельный ввод: точная локальная ошибка, фокус в поле, POST отсутствует.
4. Вставить 20 000 символов, затем 20 001 (например, скопировать в поле результат `'я'.repeat(20000)` / `'я'.repeat(20001)` из консоли). Оба ввода отправляются целиком; первый успешен, второй даёт точный текст 413 и request_id. Повторить с astral-символом `'😀'`, чтобы исключить клиентский лимит по UTF-16.
5. Остановить сервер Ctrl+C и перезапустить с `--llm fail`: отправка даёт точный текст 502 и request_id. Затем с `--llm slow`: примерно через 10 секунд текст 504, а не локальный тайм-аут UI. Это существующие режимы FakeLLM.
6. После ошибки ввод остаётся, редактирование не убирает ошибку, новая отправка убирает её. После успеха редактирование скрывает результат. Перезагрузка возвращает пустое состояние.

## Контролируемые ответы для UI

Вкладка остаётся на локальном сервере. До отправки установить в консоли браузера тестовую подмену fetch (не код приложения):

```js
window.fixtureStatus = 200;
window.fixtureBody = {
  summary: 'Контрольный результат',
  risks: [1, 2, 3].map(line => ({
    file: 'example.txt', line, evidence: '  строка\n    продолжение', risk: 'Риск ' + line
  })),
  checks: ['Первая проверка', 'Вторая проверка'],
  request_id: '0123456789abcdef0123456789abcdef'
};
window.fixtureDelay = 0;
window.fetch = () => new Promise(resolve => setTimeout(() => resolve(
  new Response(JSON.stringify(window.fixtureBody), {
    status: window.fixtureStatus, headers: {'Content-Type': 'application/json'}
  })
), window.fixtureDelay));
```

Подмена намеренно игнорирует abort для проверки поздних ответов. Менять fixture-переменные перед каждой отправкой; изменять их во время ожидания только в сценарии новой попытки. Для подсчёта вызовов поставить DevTools breakpoint на подменённом fetch. Перезагрузка восстанавливает настоящий fetch; подмены не сохранять в проекте. Проверки всех точных сообщений сверять с таблицей `specs/contract.md`.

| Сценарий | Настройка / действие | Ожидаемый результат |
| --- | --- | --- |
| Полный успех | Исходная fixture, затем risks длиной 0, 1, 2, 3 | Все поля и порядок; при 0 — «Риски не найдены»; два checks |
| Пустые проверки | `fixtureBody.checks = []` | «Список проверок пуст» |
| Неверная схема | По одному: удалить summary/request_id, risks = null, checks = [1], line = 0/1.5/"1", четвёртый риск, корень null/массив | «Некорректный ответ сервиса», без частичного успеха; доступный строковый request_id виден |
| Специальные ошибки | fixtureStatus = 422/413/504/502, fixtureBody = `{error:{code:…}, request_id:'…'}` с соответствующим кодом из контракта | Четыре точных русских текста и request_id |
| Неизвестные ошибки | Статус 500, неизвестный код, несовпавшая пара, error = null или без code | «Сервис недоступен», доступный request_id показан |
| Не-JSON | Заменить fetch на `() => Promise.resolve(new Response('не JSON', {status:200}))`; повторить с 502 | «Сервис недоступен» |
| Ошибка соединения | `window.fetch = () => Promise.reject(new TypeError('test'))` | «Сервис недоступен», нет сырого исключения |
| Единственная отправка | Исходная подмена, fixtureDelay = 3000; повторные клики и submit с клавиатуры | Один вызов; поле/кнопка disabled, точные тексты загрузки; затем разблокированы |
| Срок до заголовков | fixtureDelay = 16000 | На 15-й секунде локальный тайм-аут, форма доступна; поздний успех игнорируется |
| Срок чтения body | fetch возвращает Response с ReadableStream, который не закрывается | Заголовки не завершают таймер; на 15-й секунде локальный тайм-аут |
| Новая попытка после срока | После тайм-аута отправить новую быструю fixture; дождаться старого ответа | Новый результат сохраняется; старые catch/finally не меняют форму/результат |
| Текст и доступность | В строковые поля fixture добавить `<img src=x onerror=alert(1)>`, переносы и длинный путь; пройти форму Tab, проверить screen reader | Только буквальный текст, без исполнения; читаемые строки; объявляются загрузка/успех/ошибка |

Для проверки зависшего body после перезагрузки можно установить:

```js
window.fetch = () => Promise.resolve(new Response(new ReadableStream({
  start(controller) { controller.enqueue(new TextEncoder().encode('{')); }
}), {status: 200}));
```

Перед каждой независимой проверкой схемы восстановить исходную fixture. Отдельно проверить успех непосредственно до срока и результат после срока: просроченный ответ не принимается даже при задержке callback таймера. Для случая длительной синхронной обработки использовать DevTools CPU throttling и проверить абсолютный deadline перед публикацией, не полагаясь только на setTimeout.

## Завершение приёмки

Все группы состояний и строки таблицы должны пройти; ошибки сохраняют ввод и позволяют ручной повтор. В Network при настоящей интеграции и в breakpoint подмены нет повторных вызовов. После удаления подмен перезагрузкой повторить обычный успех с FakeLLM и выполнить `sh scripts/check.sh`. В этом плане описаны проверки; фактическая UI-приёмка выполняется после реализации.

## Фактический журнал — 2026-10-27

### Автоматическая проверка без браузера

По прямому поручению человека разбор ответа и выбор ошибки проверяются из
**`sh scripts/check.sh` без браузера**. Файл `tests/test_web_ui.py` запускает
`node --test tests/web_ui.test.cjs`; runner не пропускает тесты при отсутствии
Node.js. `scripts/check.sh` не изменён. Сборка, npm-зависимости и реальная LLM
не используются.

Тесты читают встроенные script из настоящего `app/static/index.html` и исполняют
их в Node VM. Чистый классификатор проверяется на JSON-строках; обработчики формы,
текстовый рендер и модель попытки — на минимальном DOM-адаптере с управляемыми
fetch и монотонными часами. Это исполнение кода приложения, а не поиск строк
или повторение JS-правил в Python. DOM-адаптер не подтверждает layout и работу
настоящего screen reader.

| Задачи | До реализации: ожидаемый / фактический RED | После реализации: GREEN |
| --- | --- | --- |
| T001 | Исходная команда успешна: 119 passed; файл — HTML-заглушка | Локальный `.venv/bin/python -m app.server 8000 --llm ok`, GET / → 200, text/html; charset=utf-8 |
| T002–T005 | Тесты схемы: `Response classification is missing`; тест формы: `Review form is missing` | Валидные 1–3 риска, полный порядок/поля, строгие типы/обязательные поля, отказ от частичного результата, сохранение точного ввода, один POST, блокировка, текстовый DOM и скрытие успеха при редактировании |
| T006–T007 | Тест пустых списков: ожидал «Риски не найдены», фактически «СводкаРискиПроверкиcheck» | Пустые risks/checks отдельно и вместе, пустые строки и request_id допустимы, разделы и статус успеха сохраняются |
| T008–T009 | Специальные ошибки ошибочно давали «Некорректный ответ сервиса» | Все четыре точные пары, несовпадения/неизвестные пары, неверные объекты/типы, не-JSON 200/502, сеть/body, доступный строковый request_id, сохранение ошибки и очистка при повторе |
| T008, T010 | Нет таймера: ожидался один, фактически ноль; просроченный результат принимался; старый ответ заменял новый | Зависшие заголовки/body, abort и разблокировка, старые resolve/reject при новой загрузке и после нового успеха, deadline при обработке/рендере даже без callback таймера, успех в 14999 мс |

Пробельный ввод, возврат фокуса, сохранение ввода и не-JSON уже были GREEN до
реализации специальных пар ошибок и не выдавались за новые RED.
Каждый RED подтверждён запуском неизменённого hook `sh scripts/check.sh`, затем
исправлен кодом и повторён до GREEN. Итог: **120 pytest-тестов прошли**, включая
runner с **10 JS-тестами**, содержащими таблицы граничных случаев.

### Дополнительная браузерная интеграция

Выполнена в локальном headless Chrome 156 через Playwriter. Серверы запускались
штатной командой `.venv/bin/python -m app.server PORT --llm MODE` с FakeLLM
на портах 8000/8001/8002 для ok/fail/slow. Браузер не требуется для единой команды
проверки. Подмены находятся только в памяти тестовой страницы, не в приложении;
перезагрузка восстанавливает настоящий fetch.

- **PASS:** начальный пустой экран; обычный успех с настоящим API; путь с
  клавиатуры textarea → Tab → кнопка → Enter.
- **PASS:** контролируемый fetch с переключаемыми body/status, счётчиком и
  снимком запроса; 0–3 риска, две проверки, оба пустых списка, все поля/порядок,
  evidence в pre. Содержимое `<img ...>` / `<script>...</script>` остаётся текстом,
  соответствующих DOM-элементов нет. Ввод с отступами/переносами/astral сохранён.
- **PASS:** четыре специальные пары, неизвестный статус, error=null,
  некорректная схема 200; точный текст и буквальный request_id, без результата.
  Ошибка остаётся при редактировании; пробельный ввод не вызывает fetch,
  возвращает фокус в textarea.
- **PASS:** зависшие заголовки и body действительно завершают UI на 15-й
  секунде. Форма разблокирована, сигнал aborted; повторные requestSubmit во
  время ожидания не добавляют запросов. После новой успешной попытки старое
  завершение не меняет результат/ошибку/ID.
- **PASS:** настоящий API принимает 20 000 и отклоняет 20 001 символ
  для `я` и для `😀`. В Network один POST на попытку, тело содержит полный
  исходный ввод, значение textarea не обрезано.
- **PASS:** настоящий FakeLLM fail → точная ошибка 502 с ID; slow → точная
  ошибка 504 примерно через 10 секунд, не локальный тайм-аут. Перезагрузка
  возвращает пустое поле и начальное состояние.
- **PASS:** дерево доступности Chrome содержит textbox «Diff» с label,
  describedby=hint и multiline; status имеет live=polite/atomic=true,
  alert имеет live=assertive/atomic=true. При ширине 375 px main не имеет
  горизонтального переполнения. Ошибок JS не наблюдалось; в консоли есть
  ожидаемые HTTP 413/502/504 и 404 для отсутствующего favicon.

### Остаток T011

Настоящий screen reader с прослушиванием объявлений в этом headless-окружении
не запускался. Проверка его семантики деревом доступности не заменяет такую
приёмку. Поэтому **T011 оставлена незакрытой**: требуется ручное прослушивание
загрузки/успеха/ошибки. Основная реализация и автоматическая проверка завершены;
браузерные RED не заявляются — RED выполнялся автотестами до кода по поручению
человека.
