# Tasks: Веб-страница ревьюера

**Input**: `specs/001-reviewer-web-ui/{plan.md,spec.md,research.md,data-model.md,contracts/ui.md,quickstart.md}`; общий `specs/contract.md` (D1–D6), базовые требования `docs/requirements.md`.
**Organization**: Три пользовательские истории в порядке P1 → P2 → P2; 11 задач.
**Tests**: По поручению человека разбор ответа и выбор ошибки покрываются автоматическими тестами без браузера из `sh scripts/check.sh`: pytest запускает Node.js и настоящий JS из HTML, без npm-пакетов. TDD RED/GREEN фиксируется в `quickstart.md`; браузер используется дополнительно для интеграции, отображения и доступности. Изменений `scripts/check.sh` нет.
**Paths**: Все пути относительно `practices/practice_05`. Реализация — один `app/static/index.html` со встроенными CSS/JS, DOM и Fetch API, без новых зависимостей. Готовые HTTP-маршруты и API используются по общему контракту.

## Dependencies & Execution Order

```text
T001 → T002 → US1 (T003 → T004 → T005) → MVP
                     ↓
               US2 (T006 → T007)
                     ↓
               US3 (T008 → T009 → T010) → T011
```

- Setup и Foundational блокируют истории: нужен работающий сервер и управляемая приёмка.
- US1 вводит общую форму, отправку, валидацию и рендер; US2 и US3 зависят от этого каркаса, но проверяются собственными независимыми ответами.
- Семантически US3 не зависит от пустых списков US2; выбран порядок US1 → US2 → US3, поскольку обе истории изменяют один HTML и один журнал приёмки.
- В каждой истории сначала воспроизвести RED нового поведения, затем минимальный код и GREEN. В T008 временные RED-сценарии повторить непосредственно перед T010.
- T011 выполняется после всех историй. Ошибки `sh scripts/check.sh` исправлять; проверку не ослаблять.

## Parallel Examples — по историям

`[P]` не используется: задачи реализации затрагивают один `app/static/index.html`, а записи RED/GREEN — один `specs/001-reviewer-web-ui/quickstart.md`; независимых параллельных правок нет.

| История | Порядок задач | Возможное параллельное действие без правок |
| --- | --- | --- |
| US1 | T003 → T004 → T005 | После T005 одновременно проверить полный результат в одной вкладке и клавиатуру/текстовую безопасность в другой; результаты записать последовательно. |
| US2 | T006 → T007 | После T007 в разных вкладках проверить пустые риски и пустые проверки с независимыми fixtures. |
| US3 | T008 → T009 → T010 | После T010 в разных вкладках проверить матрицу HTTP-ошибок и сценарии 15-секундного срока/поздних ответов. |

Это возможности параллельной приёмки, а не зависимости или требование запускать агентов.

## Implementation Strategy

1. **MVP**: T001–T005 — доступная форма, единственная отправка, полная проверка и безопасное отображение результата US1; проверить эту историю отдельно.
2. **Increment 2**: T006–T007 — явный успех без рисков и пустые проверки.
3. **Increment 3**: T008–T010 — полная матрица ошибок, повторная попытка и общий дедлайн.
4. **Ready**: T011 — подтверждённая браузерная приёмка и зелёный `sh scripts/check.sh`. MVP — промежуточный срез; полная готовность фичи включает все три истории.
