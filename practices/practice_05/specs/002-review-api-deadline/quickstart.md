## Подготовка

- Рабочий каталог: корень проекта `practices/practice_05`.
- Python 3.10+, существующая `.venv` с pytest; активировать её для команд `python`.
- Для ручных HTTP-примеров нужен `curl`. В автоматических тестах достаточно stdlib HTTP-клиента.
- `app/static/index.html` существует: первоначально заглушка команды API, затем файл команды UI. Реальный провайдер LLM не нужен.

```sh
. .venv/bin/activate
sh scripts/check.sh
```

Ожидается compileall без ошибок и все pytest-тесты PASS. Новое поведение реализуется по TDD; подтверждённое падение теста фиксируется до реализации, итоговая проверка должна быть зелёной.

## 1. Обычный запуск и выдача страницы

В первом терминале:

```sh
python -m app.server 8000 --llm ok
```

Во втором:

```sh
curl -i http://127.0.0.1:8000/
curl -i -H 'Content-Type: application/json' --data '{"diff":"example"}' http://127.0.0.1:8000/api/reviews
```

Ожидается GET 200 с HTML UTF-8 и точными байтами `app/static/index.html`; POST 200 с `summary`, `risks`, `checks`, серверным `request_id`. В консоли одна итоговая запись POST только с тремя полями. Заглушка не обязана иметь форму: запросы выполняются curl. Проверить также 404 неизвестного маршрута и `python -m app.server --help`.

## 2. Быстрый сбой

Остановить предыдущий сервер, затем:

```sh
python -m app.server 8000 --llm fail
```

Повторить POST из шага 1. Ожидается 502 и точная структура `{"error":{"code":"llm_failed"},"request_id":"..."}`. Во всём ответе и журнале отсутствуют `demo failure`, тип исключения и traceback. GET продолжает работать. Перезапуск без параметров сохраняет порт 8000 и режим ok.

## 3. Истечение серверного срока

Остановить сервер, затем:

```sh
python -m app.server 8000 --llm slow
```

```sh
curl --max-time 15 -i -H 'Content-Type: application/json' --data '{"diff":"example"}' http://127.0.0.1:8000/api/reviews
```

Ожидается 504 `llm_timeout` примерно через 10 секунд ожидания LLM, до окончания 12-секундного вызова. После позднего завершения не возникает второго лога или нового ответа. GET / доступен во время ожидания и после него. Это ручное доказательство рабочих 10 секунд; быстрый автоматический сценарий SC-001 приведён ниже.

## 4. Приоритет валидации

В любом режиме:

```sh
curl -i -H 'Content-Type: application/json' --data 'not-json' http://127.0.0.1:8000/api/reviews
curl -i -H 'Content-Type: application/json' --data '{}' http://127.0.0.1:8000/api/reviews
curl -i -H 'Content-Type: application/json' --data '{"diff":""}' http://127.0.0.1:8000/api/reviews
```

Все ответы — немедленные 422 `invalid_request`, с собственным `request_id`, без обращения к FakeLLM. Пробельный `diff` API принимает; в slow/fail результат определяется режимом, а не валидацией.

## 5. Автоматическая матрица приёмки

Реализовать эти сценарии в pytest и запускать исключительно `sh scripts/check.sh`. Подробности структур — [data-model.md](data-model.md), интерфейсов — [HTTP](contracts/http.md) и [CLI](contracts/cli.md).

| Сценарий | Управляемое условие | Проверяемый результат |
| --- | --- | --- |
| Регрессия A | Пустое тело, неверный JSON/UTF-8, null, массив, скаляры, отсутствующий/нестроковый/пустой diff | 422, точная ошибка, uuid4 hex, calls=[] |
| Unicode-границы | 20 000 и 20 001 code points; многобайтовые, supplementary и JSON-экранированные символы | Ровно 20 000 проходят целиком; 20 001 → 413 и calls=[] |
| Нулевые вызовы при отказе | Неверный ввод + медленный/падающий FakeLLM | Ошибка входа без ожидания зависимости |
| Успех | FakeLLM с заданным словарём | 200, исходная строка передана один раз, серверный ID |
| Схема не проверяется сервером | FakeLLM с >3 рисками либо неверными типами полей словаря | 200, значения и порядок не изменены, нет invalid_llm_output |
| SC-001 | FakeLLM(delay_s=1.0), deadline_s=0.1 | 504, возврат ≤0,5 с, один вызов |
| Серверный override | Своевременный FakeLLM при положительном нестандартном deadline_s | Используется переданный бюджет; default публичного интерфейса 10.0 |
| Ранний сбой | FakeLLM(error=RuntimeError(контрольная строка)) | 502, нет строки/типа/traceback, один вызов |
| Поздний успех и сбой | Задержка >лимита; дождаться конечного завершения FakeLLM после 504 | Payload неизменен, один вызов/лог, нет threading.excepthook/traceback |
| OBS-1 | Каждый из 200/422/413/502/504 | Одна запись с тремя полезными полями, ID/статус совпадают, duration_ms ≥0; нет diff/ответа/исключения |
| HTTP-стык | Loopback-сервер на порту 0, FakeLLM | Статус/JSON не переопределяются; HTTP передаёт deadline_s=10.0, Content-Type/Length корректны |
| D1 | GET /, неизвестный GET, временно недоступный файл в тестовой среде | Байты HTML и заголовки; 404 без раскрытия локального пути |
| CLI | default, ok/slow/fail, help, неизвестный режим | Предсказуемый выбор FakeLLM; ошибка аргументов до запуска сервера |

Для проверки передачи HTTP-лимита можно наблюдать вызов публичного обработчика, не ожидая 10 секунд в каждом тесте; адаптером остаётся FakeLLM. После HTTP-тестов закрывать соединения и сервер. Точные гонки на границе времени и физическая отмена не входят в критерии приёмки.

## 6. Стыковка с командой UI

После появления настоящего `app/static/index.html` повторить GET и три режима сервера через браузер. Проверить D1–D6 по [общему контракту](../contract.md): относительный POST, точные тексты, request_id в ошибках и проверку схемы успеха. Клиентские 15 секунд и игнорирование позднего ответа проверяются отдельно на UI: штатный slow обычно даёт серверный 504 уже через 10 секунд и сам по себе не доказывает локальный UI-таймаут. До передачи HTML достаточно проверить выдачу заглушки и API.
