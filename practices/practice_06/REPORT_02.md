# Отчёт 2. Повторные атаки после исправлений

Все правки только в lab/service.py, sandbox.py не трогал, границу стенда сохранил.
После фикса make test проходит: 16 тестов курса плюс 11 моих тестов на атаки, итого 27, все ok.
Те же атаки из отчёта 1 повторил, ниже что стало.

## Что закрыл

1. SQL-инъекция. Все запросы к базе теперь параметризованные (? вместо подстановки строки).
   id профиля дополнительно проверяется, что это число. Инъекция больше не вытаскивает таблицу.

2. Чужой профиль. /profile требует токен. Клиент видит только свой профиль, чужой id дает 403.
   Сотрудник видит любой.

3. Все заказы. /orders GET требует токен и отдает клиенту только его заказы, сотруднику все.

4. Своя цена. /orders POST теперь берет цену только из каталога, поле price из тела игнорируется.

5. Подделка роли. /admin/export смотрит роль из своей сессии, а не из заголовка X-Role.
   X-Role: staff без настоящей сессии сотрудника дает 403.

6. Чужие файлы. /files требует токен, user должен совпадать с владельцем сессии.
   Клиент читает только свои файлы, до служебной заметки не дотянуться.

7. Журнал. /debug/logs доступен только сотруднику. В сам журнал больше не пишутся тело и
   заголовки, то есть пароли и токены туда не попадают.

8. XSS. Текст отзыва экранируется через html.escape, <script> превращается в безопасный текст.

9. AI-помощник. /assistant/execute требует токен. Права проверяет сервер, а не модель:
   read_file разрешен только в своей папке файлов, export_profiles и delete_tree только
   сотруднику. Даже если решение подделать и отправить напрямую, доступа у клиента нет.

10. Prompt injection. Отзывы в промпте помечены как недоверенные данные в теге <reviews>
    с явной инструкцией не выполнять команды из их текста. Это снижает шанс, что модель
    послушает отзыв. Но главная защита в пункте 9: сервер все равно не даст лишнего,
    даже если модель поддастся.

## Проверка

- make test: Ran 27 tests, OK.
- Откат service.py к исходному и прогон test_security: 11 падений. Возврат фикса: все проходят.
  Значит тесты реально ловят проблему, а не просто зеленые.

## Вывод

Главный урок: на injection нельзя полагаться только на послушание модели. Инъекцию в промпт
можно уменьшить пометкой данных, но надежно спасает проверка прав на стороне сервера после
решения модели. Пока execute доверял решению вслепую, дырой было все остальное.
